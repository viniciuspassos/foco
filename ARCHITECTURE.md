# Architecture

## Status and scope

This document describes the implemented design.

Foco is a small, English-language browser application for breaking one or more tasks into short, checkable steps. It does not use XP, points, paid API calls, accounts, or a backend.

## Technology

- HTML and CSS for the interface.
- TypeScript for browser logic and explicit domain types.
- Vite for local development and static production builds; no UI framework.
- The browser's on-device Prompt API for optional step suggestions in English.
- In-memory application state. No localStorage, database, cookies, or server persistence.

The current target is desktop Chrome on a MacBook M2 with 16 GB of memory. The installed Chrome has the Prompt API enabled and an on-device model ready. Runtime availability must still be checked because browser and device state can change.

The `dist/` directory is generated by the build and is not committed as source.

## User flow

1. The user creates a task with a title and an optional note, both in English.
2. The user adds steps manually or requests AI suggestions.
3. For suggestions, the app checks Prompt API availability, sends the task title and note as English context, and asks for a short ordered list of concrete, actionable steps.
4. The app validates the response and shows it as a draft. The user can edit, remove, or accept suggested steps before they become task steps.
5. Checkboxes mark steps complete. The task shows a progress bar and a clear `Completed` state when all its steps are done.
6. The user removes a completed task explicitly. Reloading or closing the page clears all tasks.

If the Prompt API is unavailable or generation fails, the user can still add steps manually. The app should explain the failure in plain English and must not silently make a paid network request.

## Boundaries

`tasks.ts` owns task state transitions and progress rules. UI code displays those results and triggers operations. `suggestions.ts` owns browser AI availability, prompting, and response validation behind a small interface; it does not modify task state. This separation allows deterministic tests with a named fake AI provider.

Task titles and notes are sent only to the on-device browser model during suggestion generation. No application server receives them. The initial model download is managed by Chrome and may require a network connection; subsequent inference runs locally according to Chrome's on-device AI behavior.

## Validation and delivery

Behavior tests cover task creation, updates, step completion, progress, removal, suggestion parsing, and unavailable AI responses. Browser checks cover creating a task, reviewing suggestions, completing it, and clearing it by reload. The project provides `npm test`, `npm run lint`, `npm run build`, and `npm run format:check`.

A Vite production build produces static files for hosting. Development and AI testing should use localhost or a supported web origin; direct `file://` use is not assumed to support the Prompt API.

## Decisions requiring runtime verification

- Test the actual English suggestion quality on representative tasks before settling the prompt and response format.
- Confirm the Prompt API behavior on the final hosting origin and document its browser requirements.
